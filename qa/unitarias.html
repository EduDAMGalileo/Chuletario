Pruebas unitarias

El nivel más bajo de la pirámide: probar una función o clase aislada. El patrón AAA, los dobles de prueba, la cobertura, TDD y las herramientas de cada lenguaje.

La idea

Una prueba unitaria comprueba una «unidad» de código —normalmente un método o una clase— de forma aislada del resto. Son la base de la pirámide de pruebas: muchas, rápidas y baratas.

Por qué importan

Rápidasmiles en segundos; se lanzan a cada cambio
Precisassi fallan, señalan exactamente qué se rompió
Red de seguridadpermiten refactorizar sin miedo

1Qué es una prueba unitaria

Prueba una unidad de código sin depender de nada externo: sin base de datos, sin red, sin ficheros. Solo la lógica de esa pieza. Por eso son deterministas y vuelan.

Unidadlo más pequeño con sentido propio: un método, una clase
Aisladasus dependencias se sustituyen por dobles (sección 4)
Caja blancaquien programa la escribe conociendo el código (ver caja blanca)
Automatizadase ejecuta sola, una y otra vez, sin intervención

Regla práctica: si tu «prueba unitaria» necesita una base de datos o Internet para pasar, ya no es unitaria: es de integración.

2El patrón AAA

Casi toda prueba unitaria tiene la misma estructura en tres pasos, que conviene separar visualmente:

Arrangepreparar: crear el objeto y los datos de entrada
Actactuar: llamar al método que se prueba
Assertafirmar: comprobar que el resultado es el esperado

Una variante en pruebas de estilo BDD es Given-When-Then (dado / cuando / entonces): es lo mismo con otros nombres. Ver BDD.

3Una buena unitaria (FIRST)

Las siglas FIRST resumen qué hace fiable a una prueba unitaria:

Fastrápida: milisegundos, para lanzar miles sin esperar
Independentindependiente: no depende de otras ni del orden
Repeatablerepetible: mismo resultado siempre, en cualquier máquina
Self-validatingse valida sola: pasa o falla, sin revisar la salida a ojo
Timelya tiempo: se escribe junto al código, no meses después

La enemiga número uno es la prueba frágil: la que falla por motivos ajenos al bug (una fecha, un orden, un dato compartido). Una suite en la que «a veces fallan cosas» deja de servir porque nadie se la cree.

4Dobles de prueba

Para aislar la unidad, sus dependencias se reemplazan por «dobles» (como los de cine). El término general es test double; hay varios tipos:

Dummyse pasa para rellenar, pero no se usa
Stubdevuelve respuestas fijas programadas
Spyun stub que además registra cómo lo llamaron
Mockse le programan expectativas y verifica que se cumplan
Fakeuna implementación real pero simplificada (una BD en memoria)

En el día a día se dice «mockear» para todo, pero la distinción importa: un stub alimenta datos de entrada; un mock comprueba interacciones de salida (que se llamó a tal método). En Java se hacen con Mockito (ver JUnit).

5Aislar dependencias

Para poder sustituir una dependencia por un doble, la clase no debe crearla ella misma, sino recibirla desde fuera. Es la inyección de dependencias.

Código fácil de probar y código bien diseñado suelen ir de la mano: si algo es difícil de testear, muchas veces es señal de que está demasiado acoplado.

6Cobertura

La cobertura de código mide qué porcentaje del código ejecutan las pruebas. Ayuda a ver zonas sin probar, pero no es una nota de calidad.

De líneasqué líneas se ejecutaron
De ramassi se probaron los dos lados de cada if
HerramientasJaCoCo (Java), coverage.py (Python), Istanbul (JS)

No persigas el 100%. Una cobertura alta con aserciones flojas no prueba nada: se ejecuta el código pero no se comprueba el resultado. Mejor 80% con buenas aserciones que 100% vacío.

7TDD

Test-Driven Development: escribir la prueba antes que el código. Un ciclo corto que se repite:

1Rojotest que falla
›
2Verdecódigo mínimo
›
3Refactorlimpiar
Rojoescribes un test de algo que aún no existe; falla
Verdeescribes lo mínimo para que pase
Refactormejoras el código con la red de seguridad del test

TDD obliga a pensar primero en qué debe hacer el código y produce diseños fáciles de probar. No es obligatorio, pero es una técnica muy ligada a las pruebas unitarias.

8Herramientas por lenguaje

JavaScriptJest, Vitest, Mocha + Chai
C#xUnit, NUnit, MSTest; Moq

Todos comparten las mismas ideas (anotar tests, aserciones, dobles, ciclo de vida); cambia la sintaxis. La chuleta detallada de Java es JUnit.

9Buenas prácticas

Nombres que explicanmetodo_situacion_resultadoEsperado
Probar los bordesnulo, vacío, cero, negativo, el límite y el error
Sin lógica en el testnada de if o bucles: el test debe ser obvio
Rápidas y sin E/Ssi toca red o disco, es de integración
Se ejecutan en CIen cada cambio (ver GitHub Actions)

Siguiente nivel: cuando varias unidades ya funcionan por separado, toca comprobar que encajan entre sí. Eso son las pruebas de integración.
