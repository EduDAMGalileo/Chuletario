Pruebas de integración

Comprobar que varias piezas funcionan juntas: módulos, base de datos y APIs externas. Estrategias, cuándo usar dobles o servicios reales, y las herramientas.

La idea

Una unidad puede funcionar sola y romperse al conectarla con otra. Las pruebas de integración comprueban justo eso: que las piezas encajan —los módulos entre sí, con la base de datos o con servicios externos.

El nivel intermedio

Por debajounitarias: cada pieza aislada
Aquíintegración: las piezas conectadas
Por encimasistema: la aplicación entera

1Qué es la integración

Prueba la interacción entre dos o más componentes que ya se probaron por separado. El objetivo son las costuras: las interfaces por donde se comunican, donde suelen esconderse los fallos.

Qué cazadatos con formato distinto, contratos mal entendidos, configuración
Qué NO cazala lógica interna de cada pieza (para eso están las unitarias)
Velocidadmás lentas que las unitarias: tocan recursos reales

Ejemplo típico: la unidad «Servicio» y la unidad «Repositorio» pasan sus tests, pero al unirlas la consulta SQL no devuelve lo que el servicio espera. Eso solo lo ve una prueba de integración.

2Frente a las unitarias

Alcanceunitaria: una pieza · integración: varias juntas
Dependenciasunitaria: sustituidas por dobles · integración: reales (BD, API)
Velocidadunitaria: milisegundos · integración: décimas o segundos
Al fallarunitaria: sabes la pieza · integración: hay que investigar la costura
Cantidadmuchas unitarias, bastantes menos de integración

En la pirámide de pruebas, la integración es la franja del medio: menos numerosa que la base unitaria, más que la cima de sistema.

3Qué se integra

Módulo con módulodos partes de tu propio código que colaboran
Con la base de datosque las consultas y el mapeo (ORM) funcionan de verdad
Con una API externaque hablas bien con un servicio de terceros
Con el sistema de ficherosleer, escribir, permisos, rutas
Con una cola o cachéKafka, RabbitMQ, Redis...

La integración más habitual y valiosa es con la base de datos: es donde el código se encuentra con datos reales y donde más sorpresas aparecen.

4Estrategias

Formas de ir juntando los módulos. Cuando falta una pieza, se sustituye temporalmente:

Big bangmontar todo de golpe y probar. Simple, pero difícil de depurar
Top-downde los módulos de arriba hacia abajo; los de abajo que faltan se simulan con stubs
Bottom-upde abajo hacia arriba; los de arriba que faltan se simulan con drivers
Sándwichcombinación de las dos anteriores a la vez
Stubsimula un módulo inferior que aún no existe
Driversimula un módulo superior que llamaría al que pruebas

Incremental (top-down o bottom-up) es lo habitual: añadir módulos poco a poco hace que, cuando algo falla, sepas que ha sido lo último que conectaste.

5Dobles o servicios reales

La gran decisión: ¿usar la dependencia de verdad o un doble? Cada opción tiene su precio.

Servicio realmáxima fidelidad, pero lento, frágil y a veces con coste (una API de pago)
Doble / mockrápido y controlado, pero puede no reflejar el comportamiento real
Fake localequilibrio: una versión ligera y real (BD en memoria, servidor simulado)

Cuidado con mockear la dependencia que precisamente quieres integrar: si sustituyes la base de datos por un mock, ya no estás probando la integración con la base de datos, solo tu código. Para la BD, usa una BD de verdad (sección 6).

6Base de datos

Para probar contra una base de datos sin ensuciar la de producción, hay tres enfoques:

BD en memoriaH2, SQLite: rapidísima, pero puede diferir del motor real
Testcontainerslevanta el motor real (PostgreSQL, MySQL) en un contenedor Docker para el test
BD dedicadauna instancia solo para pruebas, que se limpia entre ellas

Testcontainers es hoy la opción preferida: prueba contra el mismo motor que usarás en producción (ver Docker), evitando las diferencias de sintaxis SQL entre gestores. Deja el estado limpio: cada test parte de datos conocidos y no depende de lo que dejó el anterior.

7APIs y contratos

Al integrar con una API (propia o de terceros) se prueba que la petición y la respuesta encajan. Y para no depender de un servicio ajeno en cada test, se simula.

Servidor simuladoWireMock, MockServer: fingen la API externa con respuestas fijas
Pruebas de APIREST Assured (Java), Postman/Newman: lanzan peticiones y validan la respuesta
Pruebas de contratoPact: verifican que quien consume y quien provee comparten el mismo «contrato»

Las pruebas de contrato resuelven un problema típico de microservicios: que un equipo cambie su API y rompa a otro sin enterarse. El contrato pactado se comprueba en el CI de ambos.

8Herramientas

Java / Spring@SpringBootTest levanta el contexto; JUnit como base
Testcontainersdependencias reales en Docker (multi-lenguaje)
REST Assuredprobar APIs REST desde Java de forma fluida
Postman / Newmancolecciones de peticiones; Newman las lanza en el CI
WireMocksimular servicios HTTP externos
pytest / TestNGmarcos que también sirven para integración

A menudo se usa el mismo framework que en las unitarias (JUnit, pytest) pero con dependencias reales y marcando los tests como «de integración» para poder ejecutarlos por separado (más lentos).

9Buenas prácticas

Sepáralas de las unitariasetiquétalas: son lentas y no deben frenar el ciclo rápido
Estado limpiocada test prepara y limpia sus datos; nunca dependas del anterior
Entorno reproducibleTestcontainers o Docker para que funcione igual en cualquier máquina
Pocas y valiosascubre los caminos críticos, no todas las combinaciones
También en CIen un paso aparte del pipeline (ver GitHub Actions)

Siguiente nivel: cuando los módulos ya se integran bien, se prueba la aplicación completa desde el punto de vista del usuario. Eso son las pruebas de sistema y E2E.
