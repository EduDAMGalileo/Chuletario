Pruebas de sistema y E2E

La cima de la pirámide: probar la aplicación completa como lo haría un usuario. Sistema, aceptación y E2E, lo funcional y lo no funcional, y herramientas como Selenium, Cypress o Playwright.

La idea

La prueba de sistema comprueba la aplicación completa, integrada y desplegada, desde fuera y sin conocer el código. Cuando recorre un flujo entero de usuario —de la primera pantalla a la última— se llama de extremo a extremo (E2E).

Desde los ojos del usuario

Unitaria«esta función suma bien»
Integración«el servicio guarda en la BD»
Sistema / E2E«el usuario compra y recibe el correo»

1Qué es la prueba de sistema

Valida el sistema entero contra los requisitos, tratándolo como una caja negra: se interactúa por la interfaz real (web, API, app) sin mirar dentro. Es lo más parecido a lo que vive el usuario final.

Entornola app desplegada y configurada como en producción
Perspectivacaja negra: entradas y salidas, sin ver el código
Alcanceflujos completos que cruzan todos los módulos
Costelas más lentas, caras y frágiles de mantener

Aquí ya no se prueban piezas (eso fue en unitarias e integración): se prueba que el conjunto cumple lo que el cliente pidió.

2Sistema, aceptación y E2E

Tres términos muy cercanos que conviene distinguir:

De sistema¿el software cumple sus requisitos? La hace el equipo de QA
De aceptación (UAT)¿es lo que el cliente pedía? La valida el cliente o negocio
E2E (extremo a extremo)recorre un flujo completo de principio a fin; es la técnica con la que se ejecutan las dos anteriores

En la práctica se solapan: una prueba E2E automatizada de «registrarse, comprar y pagar» sirve a la vez como prueba de sistema y como base de la de aceptación.

3Funcional y no funcional

A nivel de sistema se prueban dos grandes familias. Lo funcional es un tipo transversal (se prueba en todos los niveles), pero es aquí donde se cierra de cara al usuario.

Funcionalqué hace: que cada caso de uso cumple lo esperado
No funcionalcómo lo hace: rendimiento, seguridad, usabilidad, compatibilidad

Recordatorio de Fundamentos: «funcional» no es un nivel sino un tipo de prueba. Cruza la pirámide entera, pero su validación final ocurre a nivel de sistema, sobre la app completa.

4Automatizar la web

Las pruebas E2E de una web se automatizan con un navegador controlado por código. Las tres herramientas dominantes:

Seleniumel veterano; multi-lenguaje y multi-navegador (WebDriver). Muy extendido
Cypressmoderno, en JavaScript; muy cómodo para depurar, centrado en el navegador
Playwrightde Microsoft; rápido, multi-navegador, con esperas automáticas. En auge

Cypress y Playwright traen esperas automáticas (esperan a que el elemento aparezca), lo que evita gran parte de la fragilidad clásica de Selenium con los sleep a mano.

5Localizar elementos

El test necesita «encontrar» los botones y campos de la página. Cómo los localizas decide lo frágil que será.

Por id#usuario: estable y rápido, el preferido
Atributo de test[data-testid=login]: puesto a propósito para las pruebas; muy robusto
Por texto / rol«el botón que dice Entrar»: legible y cercano al usuario
CSS / XPathselectores de ruta; potentes pero se rompen si cambia el diseño

Evita los selectores atados al diseño (clases CSS de estilo, rutas XPath largas): un retoque visual inofensivo rompe la prueba. Un data-testid puesto por el equipo de desarrollo sobrevive a los cambios de aspecto.

6Pruebas de API

No todo sistema tiene interfaz web. Muchas pruebas de sistema atacan directamente la API: son más rápidas y estables que las de navegador.

Postmancolecciones de peticiones con validaciones; Newman las lanza en el CI
REST Assuredprobar APIs REST desde Java, junto a JUnit
Comprobacionescódigo de estado, cuerpo de la respuesta, cabeceras, tiempo

Prueba a nivel de API lo que puedas y reserva el navegador (más lento y frágil) para los flujos que de verdad necesitan interfaz. Ver la base de HTTP en HTTP.

7No funcionales

Se comprueban sobre el sistema completo, porque miden propiedades del conjunto:

Rendimiento / cargacómo aguanta bajo demanda · JMeter, k6, Gatling
Estréshasta dónde resiste antes de romperse
Seguridadque resiste ataques (ver Pentest)
Usabilidadque es fácil de usar (a menudo manual)
Compatibilidaddistintos navegadores, dispositivos y sistemas

Las de carga (JMeter, k6) simulan cientos o miles de usuarios a la vez para ver tiempos de respuesta y el punto en que el sistema empieza a degradarse.

8BDD y aceptación

El desarrollo guiado por comportamiento (BDD) escribe las pruebas de aceptación en lenguaje casi natural, para que negocio y desarrollo las entiendan igual. El formato es Gherkin:

Cucumberejecuta los .feature de Gherkin (Java, Ruby...)
Behave / SpecFlowequivalentes en Python y .NET
Given-When-Thenel mismo AAA de las unitarias, en lenguaje de negocio

Cada línea Gherkin se conecta con un trozo de código (un step) que la ejecuta, normalmente automatizando el navegador o la API por debajo.

9La cima de la pirámide

Las pruebas de sistema y E2E son la punta de la pirámide: las más realistas, pero también las más caras. Por eso son pocas.

Pocas y críticassolo los flujos clave (registro, compra, pago), no cada detalle
El detalle, abajolos casos borde se cubren en unitarias, que son baratas
Combatir la fragilidadbuenos selectores, esperas automáticas, datos controlados
Lentas: en su hueco del CIno en cada commit; sí antes de una entrega (ver GitHub Actions)

El antipatrón es el «cono de helado»: muchas pruebas E2E y pocas unitarias. Resultado: una suite lenta, frágil y que nadie se fía de mantener. Invierte la proporción.
