La idea

JUnit ejecuta trozos de código que comprueban que tu programa hace lo que debe. Cada prueba llama a un método y afirma (assert) que el resultado es el esperado. Si no lo es, la prueba falla y sabes que algo se ha roto.

El patrón AAA

Arrangepreparar los datos y el objeto a probar
Actejecutar el método que se prueba
Assertcomprobar que el resultado es el esperado

1Qué es JUnit

Es el framework estándar de pruebas de Java. La versión actual, JUnit 5 (JUnit Jupiter), reescribió la 4 y es la que se usa hoy. Sirve sobre todo para pruebas unitarias: probar una clase o método de forma aislada.

JUnit Platformel motor que descubre y lanza las pruebas
JUnit Jupiterel modelo de escritura moderno (anotaciones y aserciones de JUnit 5)
JUnit Vintagecompatibilidad para seguir ejecutando tests de JUnit 4

Lo que importa al escribir tests es Jupiter: el paquete org.junit.jupiter.api. Cuidado al copiar ejemplos de internet: los de JUnit 4 (org.junit.Test) tienen anotaciones parecidas pero incompatibles.

2Preparar el proyecto

Con Maven, JUnit 5 entra con una sola dependencia (el starter que arrastra todo lo necesario):

src/main/javael código de la aplicación
src/test/javalos tests, en el mismo paquete que la clase que prueban
scope testla dependencia solo existe al probar, no en producción
Convenciónla prueba de Calculadora se llama CalculadoraTest

Los IDEs (IntelliJ, Eclipse) traen JUnit 5 integrado: puedes crear y lanzar tests sin tocar el pom.xml, aunque para mvn test la dependencia sí hace falta.

El import static de Assertions.* permite escribir assertEquals(...) en vez de Assertions.assertEquals(...). Y un nombre descriptivo del test (qué se prueba, con qué, qué se espera) documenta mejor que un comentario.

4Aserciones

Las comprobaciones. Todas están en Assertions. El valor esperado va primero.

assertEquals(esp, real)son iguales (usa equals)
assertTrue(cond) / assertFalsela condición es verdadera / falsa
assertNull(x) / assertNotNulles nulo / no lo es
assertSame(a, b)son el mismo objeto (==), no solo iguales
assertArrayEquals(a, b)los arrays coinciden elemento a elemento
assertThrows(Ex.class, ...)el código lanza esa excepción
assertAll(...)agrupa varias aserciones; las evalúa todas
fail("mensaje")forzar el fallo (para caminos que no deberían ocurrir)

Con decimales (double) no uses assertEquals a secas: usa la versión con tolerancia, assertEquals(0.3, x, 0.0001), porque los double arrastran errores de redondeo.

5Ciclo de vida

Métodos que se ejecutan alrededor de los tests para preparar y limpiar. Evitan repetir el Arrange en cada prueba.

@BeforeEachantes de cada test (preparar un objeto limpio)
@AfterEachdespués de cada test (cerrar recursos)
@BeforeAlluna vez, antes de todos (debe ser static)
@AfterAlluna vez, al final (debe ser static)

Cada test debe ser independiente: por eso @BeforeEach crea un objeto nuevo. Si compartes estado entre tests, el orden pasa a importar y aparecen fallos fantasma.

6Anotaciones útiles

@DisplayName("...")nombre legible del test en el informe
@Disabled("motivo")saltar un test temporalmente
@Nestedagrupar tests relacionados en una clase interna
@Tag("lento")etiquetar para filtrar qué se ejecuta
@RepeatedTest(5)repetir el mismo test varias veces

@Nested ayuda a organizar: una clase interna «Cuando la cuenta está vacía» con sus tests dentro se lee casi como una frase en el informe.

7Pruebas parametrizadas

Ejecutar el mismo test con varios juegos de datos, sin copiarlo. Se usa @ParameterizedTest en vez de @Test y una fuente de datos.

@ValueSourceuna lista de valores simples (ints, strings...)
@CsvSourcevarias filas con varios argumentos cada una
@MethodSourcelos datos los genera un método (casos complejos)
@EnumSourceun valor por cada constante de un enum
@NullAndEmptySourceprueba con null y con vacío

8Excepciones y tiempo

Comprobar que un método lanza la excepción correcta es tan importante como comprobar el resultado feliz. assertThrows devuelve la excepción para inspeccionarla.

assertThrowsafirma que se lanza esa excepción (o subclase)
assertDoesNotThrowafirma que no lanza ninguna
assertTimeoutel código termina dentro del tiempo dado
@Timeout(2)lo mismo como anotación (segundos)

El código que debe fallar va dentro de una lambda (() -> ...): así JUnit lo ejecuta él y captura la excepción, en vez de que reviente el test antes de tiempo. Ver Excepciones.

9Suposiciones

Las assumptions permiten saltar un test si no se cumple una condición, en vez de fallarlo. Útil para pruebas que solo tienen sentido en cierto entorno.

assumeTrue(cond)seguir solo si se cumple; si no, se omite
assumeFalse(cond)al revés
@EnabledOnOs(...)habilitar según el sistema operativo

Diferencia clave: una aserción fallida marca el test en rojo (hay un bug); una suposición no cumplida lo deja omitido (no aplicaba).

10Mocks con Mockito

Para probar una clase de forma aislada hay que sustituir sus dependencias (una base de datos, un servicio) por dobles falsos. La librería estándar es Mockito.

mock(Clase.class)crea un doble que no hace nada por defecto
when(...).thenReturn(...)programa qué devuelve una llamada
verify(mock).metodo()afirma que se llamó (y cuántas veces)
@Mock / @InjectMockscrear e inyectar mocks por anotación

Un mock es un doble de prueba; ver los tipos (stub, fake, spy) en Pruebas unitarias. Mockito es una dependencia aparte del pom.xml.
