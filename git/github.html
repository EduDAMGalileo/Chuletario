Git y GitHub no son lo mismo

Git es el sistema de control de versiones (ver Git). GitHub es una plataforma web que aloja repositorios Git y añade forks, pull requests, revisión de código e issues.

1GitHub y los remotos

Un remoto es una copia del repositorio en un servidor. origin es el nombre habitual del remoto principal.

origintu remoto (normalmente, tu repo en GitHub)
upstreampor convenio, el repo original del que hiciste fork
-uasocia la rama local con la remota; luego basta git push

2Clonar y sincronizar

fetchdescarga los cambios pero no toca tu rama
pullfetch + merge en un paso
pull --rebasehistorial más limpio, sin commits de merge

Haz pull antes de empezar a trabajar y antes de push: reduces los conflictos. El día a día de Git está en su propia chuleta.

3Autenticación

GitHub ya no acepta la contraseña de la cuenta para git push. Hay dos formas:

Token (HTTPS)un Personal Access Token que se usa como contraseña
Clave SSHun par de claves; no pide nada en cada push

Con SSH la URL es git@github.com:usuario/repo.git; con HTTPS es https://github.com/usuario/repo.git. Más sobre SSH en su chuleta.

4Flujo con ramas

La norma: no se trabaja directamente en main. Cada cambio va en su rama y se integra por pull request.

Rama cortauna rama por tarea o arreglo, con nombre descriptivo
Commits clarosmensajes que expliquen el porqué
main protegidasolo se toca a través de PR revisados

5Forks

Un fork es tu copia personal de un repositorio ajeno, en tu cuenta de GitHub. Se usa cuando no tienes permiso de escritura en el original: el flujo típico del open source.

origintu fork (tienes permiso de escritura)
upstreamel proyecto original (solo lectura para ti)

Con permiso de escritura en el repo (tu equipo), no hace falta fork: trabajas con ramas directamente. El fork es para contribuir «desde fuera».

6Pull requests

Un pull request (PR) propone integrar los cambios de una rama en otra. Es donde se revisa, se debate y se aprueba el código antes de mezclarlo.

Base ← comparerama destino ← rama con tus cambios
Descripciónqué cambia y por qué; enlaza el issue (Closes #12)
Draftborrador: aún no listo para revisar
Checkslas pruebas automáticas deben pasar
Actualizarhaces push a la rama y el PR se actualiza solo

Desde un fork, el PR va de tu-usuario:feature hacia autor-original:main. GitHub lo detecta y ofrece abrirlo tras el push.

7Code review

Revisar el código de un PR antes de integrarlo mejora la calidad y reparte el conocimiento. En la pestaña Files changed:

Comentaren una línea concreta o en el conjunto
Approveel código está listo para integrarse
Request changeshay que corregir cosas antes de mezclar
Commentobservaciones sin aprobar ni rechazar
Suggestionpropones un cambio de código que se aplica con un clic

Como autor: responde a cada comentario, corrige y vuelve a pedir revisión. Como revisor: sé concreto y amable; comenta el código, no a la persona.

8Mantener el fork al día

Mientras trabajas, el proyecto original avanza. Sincroniza tu fork con upstream para no quedarte atrás:

Si tu PR tiene conflictos con la rama base, actualiza tu rama con los últimos cambios, resuélvelos en local y vuelve a subir.

Cuidado: no reescribas el historial (rebase, push --force) de una rama que otros ya estén usando. En tu propia rama de PR suele ser seguro; en main compartida, no.

9Issues y proyectos

Issueuna tarea, error o propuesta; la unidad de trabajo
Labelsetiquetas: bug, enhancement, good first issue
Milestoneagrupa issues hacia un objetivo o versión
Projectstablero tipo kanban con las tareas
Assigneesquién se encarga

En un commit o PR, escribir Closes #42 o Fixes #42 cierra automáticamente el issue 42 al integrarse. good first issue marca tareas fáciles para empezar a colaborar.

11Licencias

La licencia dice qué se puede hacer con el código. Sin licencia, el código no es libre: por defecto, todos los derechos reservados.

MITpermisiva: usar casi sin condiciones, citando al autor
Apache 2.0permisiva, con cláusula de patentes
BSDpermisiva, parecida a MIT
GPL v3copyleft: lo derivado debe seguir siendo libre con la misma licencia
AGPLcomo GPL, y también si se ofrece por red (SaaS)
Creative Commonspara contenidos (textos, imágenes), no para código

Permisiva (MIT, Apache) = casi todo vale. Copyleft (GPL) = obliga a compartir igual lo derivado. El fichero LICENSE en la raíz del repo la declara.
